Hexagon Bridge

Make the Hexagon NPU reachable for models nobody converted for you — and prove, on the laptop itself, that the NPU is really what ran them.

Snapdragon® AI Lab Build & Present Challenge 2026  ·  Rishi (RishiMaara)  ·  github.com/RishiMaara/Dragonn  ·  MIT licensed

The problem

A Snapdragon X Elite laptop ships with a 45 TOPS Hexagon NPU. For any model that isn't already in a vendor catalog — a fine-tune, a newer checkpoint — getting it onto that NPU fails in ways that produce no error message:

  • The standard quantization recipe (quantize_dynamic) cost MobileNetV2 72 points of accuracy on a real X Elite, and crashed the device runtime outright on Whisper-base.
  • ONNX Runtime's documented provider argument silently yields a CPU-only session while the application logs say NPU.
  • A model can pass every local check and still be rejected by the chip — in this project's case over one sign bit, on one input, of one operator type.

Every one of those failures is silent. The application works. The battery doesn't.

What I built

ComponentWhat it does
Scanner Answers "will this model run on the Hexagon NPU, and if not, which operators and why" on any Windows PC, with no Snapdragon device present: static operator and precision rules first, then Qualcomm's own HTP compiler run locally in about four seconds.
Converter Static a16w8 QDQ quantization done the QNN-specific way, calibrated on real data, including the fixes that appear in no quickstart guide.
Validator Runs the model on a real Snapdragon X Elite through Qualcomm AI Hub and reconciles the prediction against what the device actually did.
Application Offline speech-to-text server (OpenAI-compatible API) and dashboard that report the execution provider that actually attached — never the one requested.

It composes what already exists rather than reinventing it: ONNX Runtime's strict no-CPU-fallback session, Microsoft Olive's attention-mask surgery, Qualcomm's own mask convention and AI Hub models. The gap it fills is diagnosis — ONNX Runtime's strict mode answers yes or no, AI Hub needs a cloud upload per model, and Olive applies a fix only once you already know which one you need.

MobileNetV2 is the clearest case of the trap this project exists for: quantized the naive way it passes every placement check — one NPU graph, nothing left on CPU — and classifies 7% of images correctly. It needs per-channel weights, and nothing in the toolchain tells you that.

Against Qualcomm's own NPU Whisper

Qualcomm publishes Whisper-Tiny pre-compiled for each chipset. Running their X Elite build on the same device, through the same harness: their encoder 25.0 ms, this pipeline's 17.8 ms. Their decoder — the piece this project does not yet run on the NPU — is 2.60 ms per token, 509 of 509 layers on the NPU. Read honestly: the two models are not the same graph (Qualcomm restructures attention and stays in float, this pipeline quantizes), so this shows a general-purpose conversion path landing in the same league as the vendor's hand-optimised build, not a benchmark win.

Running it on a Snapdragon-powered HP PC

One command: powershell -ExecutionPolicy Bypass -File .\setup-snapdragon.ps1. It refuses to pass quietly — it checks for ARM64-native Python (x64 Python under emulation can never load QnnHtp.dll), installs the device dependencies, confirms ONNX Runtime can see the Hexagon NPU and names the driver version if it can't, then builds a session with CPU fallback disabled, so "runs on the NPU" is proven on that laptop rather than assumed. The pre-flight scanner itself needs no Snapdragon hardware at all.

What I did not prove

  • Only the encoder runs on the NPU here. The decoder still runs on CPU, so the speedups quoted are encoder speedups. Qualcomm's decoder measurement shows a decoder can live on the NPU; wiring it into this application needs a physical device to verify.
  • Speedup depends on the CPU baseline: 24–57× against AI Hub's CPU numbers, but only 4–10× against a well-tuned CPU.
  • No power or battery measurement. AI Hub does not expose it — the efficiency argument for an NPU is the one thing I could not measure.
  • MiniLM loses retrieval quality (75.0% same top hit vs FP32). An embedding cosine of 0.987 looks fine and hides it; a16w8 is not free for every model.
  • One of my own claims was corrected by the hardware: the scanner used to report that dynamic quantization means 0% NPU. On the device, a naive CLIP ran 450 of 450 layers on the NPU. The rule now reports an unsupported format and defers to the compiler and the device.
